电信领域的小模型怎么选？从 Agent 与问答场景判断 4B、9B、14B

2026年11月9日
AI
/独立开发
阅读需 7 分钟

如果要做一个电信垂直领域的小模型，主要承担两个任务：Agent 工具调用和专业知识问答，该从多少参数开始？

很多讨论一上来就争 7B、14B 还是 32B。但“电信领域”不是一个单独的推理任务，而是跨越网络术语、规范理解、系统操作与流程判断的一组任务。同样是问答，解释某个术语与综合多个版本的网络配置规范，难度可能完全不同；同样是 Agent，选择查询接口与执行有影响的变更操作，对可靠性的要求也不同。

一个可执行的起点是：以 8B～14B 级别的指令模型做联合基线，先接入 RAG 与只读工具；再用 3B～4B 级别测试轻量意图分类，必要时才比较更大的模型。 这是评测起步建议，不是声称这些参数量已经在某个电信生产环境中验证成功。

先将两个目标拆开：问答不等于 Agent​

子场景模型主要做什么可能先限制性能的因素
术语、流程、规范问答理解问题，从受控知识库检索并组织有引用的答案文档检索质量、版本匹配、引用与拒答机制
多文档故障分析辅助组合日志、告警和规范证据，给出排查顺序跨文档推理、上下文长度、事实冲突
Agent 查询工具选择正确接口、填写参数、解释工具返回值工具选择准确率、JSON 参数、错误恢复
Agent 执行操作在明确授权下提出或执行动作权限控制、审批、幂等性、审计与回滚

专业词汇多，不意味着一定要先扩大模型。国际电信联盟 ITU-T 的电信生成式 AI 技术报告将领域知识适配、指令遵循和特定用例评估分开讨论，并明确列出 RAG 和微调两条领域知识适配路径：ITU-T TR.GenAI-Telecom（2025）。

参数量怎么选：先选评测梯度，不要直接赌一个数字​

参数规模可以先验证的职责不宜预设它能做好什么
3B～4B意图识别、任务路由、简单字段抽取、受限分类复杂跨文档推理和长链工具规划
7B～9BRAG 问答、单步与少量多步工具调用的首个基线未经测试就承担复杂网络变更
14B 左右当中小模型在技术理解、工具参数、证据整合上不足时的对照组仅凭参数更大就认定成本收益更好
27B～32B 及以上困难样本的质量上限、复杂 Agent 的候选对照不测吞吐、时延、并发与显存就直接定为全量模型

举例来说，开源权重模型可以先选 Qwen3-8B、Qwen3.5-9B 和 Qwen3-14B 做不同规模的测试。它们不是“已证明最适合电信”的排行榜，只是来源、参数规模和模型卡明确、便于建立可重复基线的候选。选择时还需要核实具体权重版本、许可证、模型格式和推理框架兼容性。

尤其要分清总参数与 MoE 每 token 激活参数：例如 30B-A3B 不等于“只需存放 3B 参数”的模型。部署显存、吞吐和推理成本仍须针对实际架构与框架测量，不能把参数量直接换成承诺的并发数。参见 Qwen 模型命名和结构说明。

粗略显存估算，只能用于排除明显不合适的方案​

纯权重在理想化条件下，FP16/BF16 大约是每个参数 2 字节：8B 约 16 GB、9B 约 18 GB、14B 约 28 GB。四位权重量化的理论下界约为其四分之一，但真实显存还包括量化元数据、KV Cache、批处理、上下文长度、模型附加组件和推理框架开销。

因此，不要因为“14B 的权重大约 28GB”就断言一张 32GB 显卡能满足目标并发；也不要因为模型标称支持很长上下文，就认为把所有规范一次塞进提示词比做好检索更可靠。

专业问答：建议先做 RAG，别急着用行业材料微调​

对于不断更新的标准、操作规程、设备手册、产品与系统说明，第一版更适合采用：

用户问题
  → 识别任务与访问权限
  → 检索经过授权的电信文档
  → 按版本/日期/适用范围重排证据
  → 小模型回答，并给出来源
  → 证据不足时说明“不确定”

重点在检索语料治理：同一术语可能出现在不同版本的规范中，同一个配置参数也可能具有厂商、网络制式、软件版本上的限制。知识库至少应该保存来源、版本、日期、适用范围和访问权限，并在答案中引用实际命中的材料。

RAG 不能天然消除幻觉。需要专项测试：没有检索结果时能否拒答；检索到过期文档时是否能发现冲突；只有部分证据时是否会把推测说成结论。

什么时候考虑 LoRA/SFT？不是因为模型“不知道所有电信知识”，而是在检索证据正确的前提下，仍然经常出现稳定、可归因的输出行为错误，例如专业实体抽取不稳、格式不合格、特定工具参数总是填错。这时使用经过审查的指令样本做小规模微调，再与原模型对照验证，通常比先训练一个从头开始的“电信模型”更容易定位收益。

Agent：工具调用准确率比聊天流畅度更重要​

Agent 的最初目标可以非常窄：给出问题后，模型应该判断是回答、检索知识库，还是调用只读接口获得最新事实。

一个概念性的只读工具定义：

{
  "name": "get_alarm_summary",
  "description": "查询用户有权限访问的网络告警摘要",
  "parameters": {
    "type": "object",
    "properties": {
      "resource_id": { "type": "string" },
      "time_range": { "type": "string" }
    },
    "required": ["resource_id", "time_range"]
  }
}

这里的工具名和字段纯属设计示例，不代表某运营商或厂商的真实接口。调用前，应用层仍必须校验资源权限、参数范围和身份；工具输出不能被模型自行“补造”。

Qwen 的函数调用说明和 vLLM Tool Calling 文档说明了如何让模型选择工具与输出结构化参数。但能够生成符合 JSON Schema 的参数，不代表选择的工具正确、数据源真实或操作已经被授权。

对于配置下发、工单关闭、策略调整等可能影响生产系统的写操作，不应以一次自然语言工具调用作为唯一安全关卡。至少需要明确的权限范围、动作预览、人类审批（适用时）、幂等保护、审计记录与失败回滚。第一阶段最好只做读取、诊断建议和草拟操作计划。

实际怎么选：一次最小评测就能排除很多猜测​

与其讨论“8B 是否够用”，不如准备一组具有代表性的已脱敏或合成任务。下面是一个起步测试规模的示例，不是行业统一标准：

评测集示例数量核心判据
术语与规范问答100正确性、来源是否支持结论、是否识别版本
多文档排障问答50故障定位步骤、证据冲突处理、合理拒答
单步工具调用50选对工具、参数完整、JSON 合法、权限条件
多步 Agent 流程30工具顺序、失败恢复、无越权动作
无答案/越权/过期资料30拒答准确率、未授权信息是否泄漏

不要用最终用户的全部请求直接训练或评测；先完成敏感数据审批、访问控制与必要脱敏。所有模型对照应使用相同的文档版本、检索管线、工具列表、上下文预算和可接受的资源配置。对于任务失败，至少区分“检索没找到”“模型理解错”“模型选错工具”“工具调用失败”“权限阻止”五类来源。

建议分两轮：

  1. 第一轮能力筛选：7B～9B 与 14B 对比知识问答和只读 Agent 的任务成功率。测试要包含明确反例，不只比较模型口才。
  2. 第二轮资源筛选：在接近真实的输入长度与并发下测 p50/p95 时延、请求成功率、GPU 显存、实际吞吐，以及超时和失败恢复。

当更小模型已经达到业务验收门槛，而更大模型只增加少量质量收益却显著增加成本时，优先选择小模型更合理；如果关键错误集中在长链推理和多步工具执行，则保留大模型作为困难请求的回退选项，比要求所有请求都走大模型更值得测试。

建议的第一版架构​

                ┌→ 电信知识库检索（RAG） ─┐
用户请求 → 意图路由 ┤                         ├→ 统一答案与来源
                └→ 受控只读业务工具 ────────┘
                       ↓
               权限校验 / 审计
                       ↓
               8B～14B 基线模型
                       ↓
           不确定 / 高风险 → 人工复核

不必为了“垂直领域”同时建设所有组件。最小可行版本可以是一套 8B～9B 模型、受控文档检索、少量只读工具与完整评测日志；当它在明确的样本上表现不足，再引入 14B 级别模型或对稳定错误做定向微调。

最终建议：如果尚无评测数据，就不要先定死参数量。先用 8B～9B 做首轮联合验证，拿 14B 做质量对照，3B～4B 只评估路由/抽取等较窄职责；复杂流程是否需要 27B～32B，由错误分布和资源测量决定。

这条路线不是“参数越小越好”，而是先证明系统在哪个环节失效，再决定该补知识、改流程、做微调，还是升级模型。
