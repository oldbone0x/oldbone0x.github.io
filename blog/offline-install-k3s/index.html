K3s 离线安装指南：Air-gap 镜像准备、部署与私有仓库排查

2026年1月6日
系列：离线部署
/devops
/docker
阅读需 6 分钟

没有外网连接的 Linux 服务器也能安装 K3s，但只传一个 k3s 可执行文件并不够：还需要为同一版本、同一架构准备集群组件镜像、安装脚本，以及可能用到的 SELinux 策略包。先选定镜像交付方法，再安装，通常比遇到 ImagePullBackOff 后逐个补镜像更容易排查。

这篇整理 K3s 官方的 Air-gap 安装流程与容易被忽略的安全边界，不是当前环境的运行测试报告。旧版文章中的命令与终端输出已撤下；在不同发行版和 K3s 版本上执行前，请对照官方文档重新检查兼容性。本文资料核对于 2026-11-09。

先明确：你属于哪一种离线部署？​

条件更直接的方法需要特别留意
小型集群，无法运行独立镜像仓库手动放置 Air-gap 镜像包每个需要镜像的节点都要准备匹配的归档
已有在隔离网络中可达的 OCI 镜像仓库私有仓库镜像方法镜像需提前推送，节点配置 mirror 与证书
只是主机禁止访问互联网，但内网有其他网络服务先画清网络边界再选方案“无法访问外网”不等于主机没有默认路由或内网 DNS

官方同时支持上述两种常见路径：K3s Air-Gap Install。下面主要介绍单节点、手动放镜像包的入门流程，多节点与高可用请继续按官方文档设计。

1. 安装前检查清单​

  • 系统与架构：确定发行版仍在支持期内，并检查 K3s 系统要求、CPU 架构、磁盘空间与内核特性。历史示例曾使用 CentOS 7.9，不应把它当作新部署的默认目标系统。
  • 版本对应：二进制文件和 Air-gap 镜像归档须来自同一 K3s release；不能随意混用不同版本。
  • 可信来源：通过 K3s Releases 选择确切版本与架构，下载并核验发布方提供的校验信息；在可联网机器准备材料后，通过受控方式传入隔离网络。
  • 网络与安全：明确节点间通信、DNS、私有镜像仓库的证书和鉴权。不要为了安装方便而将管理接口或容器网络端口暴露到公网。
  • 维护计划：提前决定离线升级、镜像替换、配置备份与故障恢复流程。

2. 准备安装材料​

在联网环境中，针对同一个已选定版本准备：

  1. 对应 CPU 架构的 k3s 二进制文件。
  2. 同一 release 的 Air-gap 镜像包，例如 AMD64 架构的 k3s-airgap-images-amd64.tar.zst（具体名称以 release 附件为准）。
  3. 官方安装脚本 install.sh，来源为 get.k3s.io；先审阅脚本内容，再放入隔离环境。
  4. 如果目标系统启用 SELinux，准备匹配系统版本的 k3s-selinux 策略包及其离线依赖，参考 SELinux 安装说明。

传输前后验证材料完整性。不要复制网络教程里某个年份的固定 RPM 下载链接，就默认它适用于现在的操作系统或新 K3s 版本。

3. 单节点手动 Air-gap 安装​

确认文件已在目标节点本地准备好，且所选 release 与系统兼容。以下步骤展示文件放置与启动路径，不是经过现场实测的通用脚本：

# 以下假设相关文件都已安全传入当前目录
sudo install -m 0755 ./k3s /usr/local/bin/k3s
sudo mkdir -p /var/lib/rancher/k3s/agent/images/
sudo cp ./k3s-airgap-images-amd64.tar.zst /var/lib/rancher/k3s/agent/images/

# 先阅读脚本内容；在离线节点上使用本地文件，而非通过 curl 在线执行
chmod +x ./install.sh
sudo env INSTALL_K3S_SKIP_DOWNLOAD=true ./install.sh

上例不设置 --write-kubeconfig-mode=644。K3s 默认以 600 权限写入管理员 kubeconfig；它包含允许管理整个集群的凭证，不能为了让任意普通用户运行 kubectl 就改为全体用户可读。必要时通过受控的管理员账户或合适的 Kubernetes 角色权限访问。K3s Cluster Access 与 Server CLI 对权限和文件用途有明确说明。

如果启用了 SELinux，先正确安装所需策略和依赖。不要将 INSTALL_K3S_SELINUX_WARN=true 当成解决安全配置问题的方法；它只会让安装脚本在缺少策略时继续执行，并不能替代策略安装。

验证安装结果​

sudo systemctl status k3s --no-pager
sudo k3s kubectl get nodes
sudo k3s kubectl get pods -A

k3s 服务成功启动，并不意味着集群中所有 Pod 都已就绪。继续检查节点状态、CoreDNS、集群网络以及镜像拉取事件。命令的预期结果会随所选 release、网络插件与环境改变，本文不提供模拟的“已成功运行”输出。

4. 防火墙：理解所需通信，而不是直接全部关闭​

K3s 的网络要求取决于单节点还是多节点、所用 Flannel 后端、是否启用嵌入式 etcd 等。官方 Requirements / Networking 列有端口和来源范围，例如：

  • TCP 6443：Kubernetes API / K3s server，限制为可信管理端和节点。
  • UDP 8472：使用 Flannel VXLAN 的节点间通信，不得对公网开放。
  • TCP 10250：部分 kubelet API / metrics 通信，依据集群角色限制。
  • 其他 CNI 或高可用部署可能有不同规则，应按实际拓扑检查。

官方在部分发行版上讨论禁用 firewalld 的兼容性方案，但它不是任意网络环境都应该直接照抄的安全默认值。先核对主机防火墙、云安全组和实际网络拓扑，再决定允许的来源与端口。

5. 另一条路线：使用私有镜像仓库​

当隔离网络有可达的 Registry 时，先将所需 K3s 镜像从联网环境迁移并推送到该 Registry，再在每个需要拉取镜像的节点设置 /etc/rancher/k3s/registries.yaml。示意配置如下：

mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.com:5000"

registry.example.com 只是文档示例域名，不是可用的仓库；必须换成节点实际能访问的内网 Registry 地址，并核对 TLS、证书和需要的认证。对于自签 CA，需要按官方配置节点的证书信任；不要随意将 insecure_skip_verify 设为 true。完整说明见 Private Registry Configuration。

注意三点：

  1. 127.0.0.1 永远指当前节点自己，不能假定所有节点都能通过这个地址找到另一台机器上的 Registry。
  2. 配置 mirror 不会自动生成或上传缺失镜像。应先校验所需镜像已存在，并排查命名空间与标签是否一致。
  3. Containerd 在默认情况下可能回退到上游 registry endpoint；完全隔离场景需要按 K3s 版本和 默认回退规则 单独检查。

如果还没有 Registry，先阅读站内 Docker 离线安装与私有仓库的注意事项。其中的历史 Registry 命令不能直接套用到生产网络。

6. 常见故障先查哪里​

现象先检查不建议的捷径
ImagePullBackOff / ErrImagePull镜像包与 K3s release 是否一致；镜像是否已导入；具体节点的 containerd 日志反复重启但不看实际拉取错误
Pod DNS 失败主机 /etc/resolv.conf 是否可用、K3s 的 --resolv-conf 选项及 CoreDNS 日志直接删除 CoreDNS 的转发配置
节点 NotReady节点状态、网络组件、内核模块、防火墙和路由全面关闭安全控制
私有 Registry 拉取失败节点实际可达性、证书、认证、镜像名和节点上的 containerd 日志使用所有节点的 127.0.0.1 或无验证明文仓库
普通用户无法读取 kubeconfig管理员访问策略、文件权限和账号角色将集群管理员凭证改为 644

排查时可先用 sudo k3s kubectl describe pod ... 查看事件，再查看Pod 所在节点的 containerd 日志（具体路径参照私有仓库官方文档），避免依据另一台节点的状态做推断。
