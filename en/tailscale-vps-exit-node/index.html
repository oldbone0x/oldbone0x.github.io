Using a Tailscale Exit Node When a VPS Stops Accepting Public Connections

My VPS still answered ping, but SSH and a service on TCP port 443 both stopped responding from the networks I tested. I tried Tailscale on the existing machine to see whether I could get a private connection without paying for another VPS.

The exit node works well enough for my everyday use. One download was only around 100 KB/s, so I would still measure performance before relying on it for large transfers. The cause of the original public connectivity problem remained unconfirmed.

Get private SSH working first

Use your hosting provider’s console to sign in to the running VPS. Install Tailscale using its Linux instructions, then sign in on the VPS and your computer so both join the same tailnet. The VPS needs outbound connectivity to Tailscale. Both devices can use an encrypted relay if they cannot establish a direct connection.

sudo tailscale up
tailscale ip -4

On your computer, SSH to the address returned by the second command using your usual username and SSH key. This uses the existing SSH service on the VPS. If the Tailscale peer responds but SSH fails, check that SSH is listening and that the server’s firewall permits your connection through the Tailscale interface. Once SSH works, you can use it to configure the exit node.

Make the VPS an exit node

On a Linux VPS with systemd, save and apply the forwarding settings, then advertise the machine as an exit node. Check any existing forwarding settings if the machine already does routing.

sudo tee /etc/sysctl.d/99-tailscale-exit-node.conf >/dev/null <<'EOF'
net.ipv4.ip_forward = 1
net.ipv6.conf.all.forwarding = 1
EOF
sudo sysctl -p /etc/sysctl.d/99-tailscale-exit-node.conf
sudo tailscale set --advertise-exit-node

In the Tailscale admin console, open the VPS’s route settings and approve it for use as an exit node. On each device you want to route through the VPS, select that exit node in the Tailscale app. Compare your public IP on the client and the VPS using the same IP-check service and address family. A matching address confirms the tested request left through the VPS. You can switch the exit node back to None and keep using Tailscale for private SSH.

Check the connection while a download is slow

Run these commands on the client while traffic is flowing. Look at the VPS entry in the status output and the path reported by the ping.

tailscale status
tailscale ping <vps-tailscale-name>
tailscale netcheck

A direct connection reaches the VPS peer to peer. If the ping output says “via DERP,” the packets went through a Tailscale relay. Tailscale may start on a relay and then upgrade to a direct path, so watch what happens after the first reply. Relays add a network hop and can limit throughput.

Download the same file once on the client through the exit node and once on the VPS itself, close together in time. If both are slow, check the download source or the VPS’s internet path. If the VPS is fast and the client stays on a slow relay, focus on the path between the client and the VPS. A single download rate cannot tell you which path was in use.

Tailscale’s performance troubleshooting guide

Who sees which IP?

Your local network can still see the source address on the outer connection and the address it connects to. On a direct path that destination is the VPS. On a relayed path it is the relay. The relay forwards encrypted WireGuard packets, and the VPS forwards the internet traffic. The site you visit sees the VPS’s exit IP and can still associate activity with your account if you sign in.
